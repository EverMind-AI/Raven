# 检查与证据：基础知识、主动补查和效果核验

本篇说明 Curator 如何取得理解材料，并判断一个改动是否真的发生作用。适用范围见[阅读入口](index.md)。本文中的预备知识资源、运行事实、方案和评价有不同来源。

## 1. 理解材料分为三个部分

| 部分 | 取得方式 | 负责回答的问题 |
|---|---|---|
| 预先准备的机制知识 | 本目录中按源码版本维护的专题材料 | Loop 如何运行，接口之间有什么关系，改动通常怎样生效 |
| 当前实例事实与有效契约 | Worker.inspect 与宿主声明 | 当前 worker 实际装了什么，本轮允许改什么 |
| 按具体缺口读取的细节 | Curator 发起只读查询，宿主执行并返回 | 当前判断还缺少哪些配置、正文、源码或组合依据 |

基础知识的预先准备减少重复读源码和重新梳理稳定机制的需要。它不能提前确定每个实例的加载结果或每次执行的事实。反过来，仅提供实例列表和源码目录，也不能代替完整的机制说明。

本目录是为上述第一部分准备的资源：阅读入口完整读入 orientation，所选目标的接入材料随生成请求交付，其余专题登记为 `reference.<文件名>` 来源按需读取，详见[阅读入口](index.md#1-适用范围)。

## 2. inspect 做什么

`Worker.inspect` 请求已经装配的运行时提供快照。适配层根据实际 origin、resident 条件和宿主限制恢复有效 Declaration，并交付 facts 与 sources。

| 材料 | 当前内容 | 使用边界 |
|---|---|---|
| 策略与组件事实 | 原生四模块、Hook、ContextEngine、记忆后端的实现信息 | 实现身份不能证明方法已经调用 |
| 工具与插件 | 检查时的默认工具定义视图、激活 manifest、MCP 状态 | 检查在 turn 外执行，不能代表任意 session 的 overlay 或实际调用数组 |
| Skill 与 Bootstrap | 发现的 Skill、可用性和原生内容文件 | 被发现不等于完整正文已进入请求 |
| 配置与已有产物 | 该代装配使用的脱敏配置、当前 Artifact 的 values 与 files | 不是会话模型选择等所有 live 状态的汇总；不能复制脱敏占位值回配置 |
| 装配证据 | assembly_evidence 保存检查时已积累的记录；运行过后也可能含执行记录 | 不是仅有启动记录，也不能覆盖所有组件内部状态 |
| 源码索引 | 原生机制与当前实现的路径、范围、内容摘要 | 可用于定向读取和版本一致性检查 |
| 简短机制描述 | 策略职责、Hook 文档和关键源码入口 | 当前摘要不是本目录所有知识的自动展开 |

inspect 本身通过代码提取事实，不请求模型“理解一遍 Raven”。Worker 将检查与执行串行化，当前接口在 turn 之间取得快照，不在执行中不断轮询。把快照交给生成流程后，该流程使用的是这份快照。特定会话的实际模型绑定、工具数组、请求和结果，应从相应执行中取得。

## 3. Curator 怎样主动补查

模型先获得任务、worker 摘要、声明视图、来源目录和已提供的证据。若仍不清楚具体机制或已有内容，可以提交查询：

| 查询 | 行为 | 边界 |
|---|---|---|
| `read_fact` | 按已知事实段和键/数组路径读取内容，支持字符分页 | 读取本轮 Context 中的快照，不是重新 inspect 活动进程 |
| `read_source` | 读取或查找已登记来源中的文本，支持字符分页 | 来源名称必须已登记，读取时检查内容摘要一致性 |
| 原生 `list_dir / find / grep / read_file` | 目录发现、跨文件搜索与按行阅读 | 读取宿主提供的源码副本、当前实现、事实与候选；目录内文件无须逐个登记 |
| 原生 `exec` | 组合命令、AST 查询和环境内检查 | 原生权限与配置的 executor；仅当前环境内的前台命令 |
| `check_candidate` | 使用当前 Plan 预检草稿并提供可读候选目录 | 独立预算；复用正式验证器；不提交、不安装，行为检查取决于宿主 probe |

`report_gap` 是另一类结束提交：说明必要事实、能力或权限缺口，当前实现结束这次生成并将原因交回调用方。它不执行补查，也不会自动向用户发起澄清。

查询结果以工具返回消息进入当前阶段的模型上下文，模型继续判断是否再查或提交。理解/选面/方案、实现、修复都使用同一查询循环，并共享有界的调用与查询预算。

宿主为一次生成准备临时探索目录：source 保留获准仓库目录的相对路径，facts.json 保存本轮实例事实，active 保存当前生成代码，candidate 保存最近一次检查的有效草稿。探索目录和排除规则通过 exploration 材料交付；外部目录和符号链接不会因文档引用而自动获准。

源码副本提供稳定阅读内容；交付前核对原始文件清单与内容、输入副本和事实，变化则拒绝本轮交付。普通文件工具只在探索目录内读取。Shell 使用 Raven 配置的执行环境；DirectExecutor 不提供操作系统隔离，源码完整性检查也不是安全沙箱。临时目录随调用结束清理，原始返回内容保留在生成 trace。

原生搜索遵循其忽略和截断规则；需要扩大覆盖时可以缩小到具体文件、按行继续阅读，或使用 exec 明确设置搜索参数和输出分段。注册来源是阅读导航，不再是全部可读文件的人工名单。

如果源码已改变，读取会拒绝把它当作原来加载版本的依据；调用方需要重新建立与运行代码一致的检查材料。模型查询结果也不能增加 Declaration 的权限。

### 3.1 从问题定位补查入口

| 需要核实的问题 | 优先读取的事实或登记来源 |
|---|---|
| 哪个阶段调用方法，结果怎样组合 | `loop.participant_timing`、`loop.participant_composition`、`loop.step_view`、`loop.execution` |
| 当前配置和既有代码是什么 | configuration、authored 事实；本轮 sources 中的 instance / generated 来源 |
| 工具如何执行、gate 怎样拒绝 | tools / plugins / mcp 事实；`loop.tool_execution`、`host.gate_contract` |
| Prompt、Skill 和历史怎样组装 | bootstrap / skills 事实；`loop.context_assembly`、`host.context_contract` |
| 工厂怎样构造、拿到什么输入 | `runtime.assembly`、`host.plugin_context`、`host.service_grants` |

这些名称是登记阅读入口；需要依赖定义或调用方时，可在 exploration.source_root 下继续搜索、读取对应文件。超出宿主提供范围的依赖仍需报告具体缺口。阅读范围不扩大 Declaration 的修改授权。

### 3.2 阶段交接中的已有结论

当前生成流程分为初选、设计和实现。初选 Selection 保存问题判断、选择依据和待查问题；设计 Plan 保存具体机制、变更预期与验证方式。实现收到当前初选和完整设计，任务、反馈、活动代码与实例事实保持同源。

跨阶段 history 由同一份 trace 派生，保留此前实际返回的查询内容及参数、失败和截断标记、显式模型说明、阶段提交、预检及正式校验结果。原生工具文本继续带有不可信资料边界。sources 同时给出已登记来源的内容摘要；长文件只读过部分时，仍需继续读取缺少的部分。历史保留的是已取得的信息，不意味着未读取的内容也已获知。

决定方案的关键前提仍应进入准确的阶段产物。history 提供原始依据，不能把它当作当前有效方案：revise_plan 或 revise_selection 后，旧 Plan、候选及其检查仅是历史证据；候选阅读目录会被清除，必须重新设计和验证。未变化的基线事实可以继续使用，依赖旧设计的结论需要重新判断。这里没有跨任务知识记忆，也不传递模型隐藏推理。

## 4. 验证是在什么环境下发生的

当前 `Worker.check` 先重新 inspect 并检查候选身份与声明，再执行 Python 源码静态检查，然后在独立进程的本地状态副本上构造候选。

各类检查发生的时机不同：

| 检查 | 实际覆盖 |
|---|---|
| 声明、候选身份与 schema | 当前选面、数据形状和内容是否能被宿主接受；失败可能直接抛出异常，不一定形成 Validation |
| 静态 Python 检查 | 解析与编译支持文件，不执行其行为 |
| 默认独立装配 | 导入入口，执行装配时需要的插件和引擎工厂，核对对应注册与绑定 |
| 可达 turn / probe | 创建该 turn 的 Participant 实例，检查选中方法，调用具体 phase 并检查返回；其他行为取决于 probe 实际做了什么 |

默认装配只为生成 Participant 导入工厂并建立包装，不提前调用其无参构造函数。因此，“构造函数会报错的 Participant”也可能通过默认 check，直到 turn/probe 到达席位才被发现。不能把默认检查通过写成所有组件都已实例化和验证。

四策略的 JSON 数据转换在返回给消费者前，按消费者协议校验实际值；对象已构造不代表其当前字段仍然有效。转换或策略调用失败时，对应的 `*.error` 记录保留 operation、arguments 与调用前的 state，沿用执行记录中的版本和作用域归属。state 只包含该策略拥有的 JSON 状态，不代表其他组件、外部资源或已经发生的副作用。

修复运行期问题时，宿主可将实际失败输入和必要状态组成 `probe`，通过现有隔离候选检查回放，再检查相关正常路径。生成流程中的无改动候选也必须通过同一个 validate 回调；回放失败会进入现有 repair 阶段，可以修订实现或重新选择目标。当前不会自动从任意日志构造完整回放，也不会自动重试正式任务；缺少状态或外部依赖时，必须明确验证边界。回放通过只证明所执行的路径，不能代替整体任务验收。

验证返回的 `validation.probe` 记录明确标注 `not_supplied`、`started` 或 `completed`；异常另外记录为 `validation.error`。`completed` 只说明给定 probe 执行完成，检查范围必须结合它实际执行的断言与原生记录判断。未提供 probe 不意味着行为通过。

默认验证运行不启动完整资源。需要验证具体行为、生命周期、MCP 或模型交互时，由宿主提供适用的 probe；生成模型当前没有自行创建并执行任意 probe 的工具。

本地状态副本用于隔离当前会话和受管理文件。外部系统、网络或任意工厂副作用不自动获得事务隔离，probe 的结论应按它实际覆盖的环境解释。

`Validation.passed` 只表示本次检查没有报告错误。未触发的方法、未启动的资源、未执行的分支和任务改善，都不能由此推断。

## 5. 当前采集了哪些执行证据

| 证据位置 | 能观察到的内容 | 不能据此直接断言 |
|---|---|---|
| 组件包装 | 工厂调用、构造结果或错误；实际绑定核对 | 组件每个内部行为都已验证 |
| Participant 包装 | 目标、phase、调用、返回、跳过、异常 | 原生 Loop 一定采纳了该返回 |
| Loop 控制观察 | turn 收尾时读取的原生回退元数据 | 不是每次控制动作的完整日志；多 attempt 时也不保证是 turn 累计值 |
| Provider 包装 | Loop/provider 边界请求、返回、流式片段和错误 | 远端最终网络 payload 与内部每次 HTTP 重试的完整轨迹 |
| Runner 事件与结果 | 原生执行事件、返回结果与关联 turn | 工具声称的效果都得到独立外部确认 |
| 生命周期记录 | MCP 状态、后端与服务启动、关闭 | 外部服务的所有内部状态 |

受观察的模型池绑定也进入 provider 包装。当前 Execution 携带 turn_id、事件、记录和 outcome，并没有自动附上 Candidate 或任务修订编号；记录文件位于对应运行进程的目录，任务版本关联仍由调用方维护。对当前版本的判断应使用与它关联的执行证据。

原生容错可能吞掉参与者异常、忽略某意见，或让缺少可选组件的执行继续。适配层保留的错误记录是重要依据，不能仅依据最终有回答来认定没有错误。

## 6. 从装配成功到任务改善

评估一项改动时，应按它的作用路径提出可检验的问题：

1. **加载**：目标代码、配置或资源是否进入该运行时？
2. **调用**：相关输入条件下，方法或资源读取是否真的发生？
3. **返回**：产生了什么结果，是否符合契约？
4. **应用**：宿主是否采纳；随后消息、工具执行或控制路径发生了什么？
5. **任务结果**：用户目标是否更好地得到满足，反馈支持哪个判断？

例如“增加 review 以避免无证据的完成声明”：应看到测试或其他证据的真实来源、review 在结果可见时被调用、必要的纠正注入、获准重采样及后续回答变化。若只看到 review 返回 resample，而回退预算已经耗尽，不能报告其成功阻止了交付。

## 7. 反馈怎样进入下一次生成

Context 可以携带当前任务、原始反馈、已有观察和上一份方案。Curator 可以据此重新理解问题，改变选面、机制或实现；验证失败也可以触发局部修复或 revise_plan。

workflow.improve 连接显式反馈、生成、验证与换版，并保留任务、执行和修订关联。Curator 本身不把每条消息自动归类为反馈；反馈解释及任务级试验、评价与迭代由同级 Analyst／Iteration 承担。

用户评价、自动评价和实际执行记录应保留来源与关联。评价中的判断可以成为改造依据，但不能替代底层执行事实；模型提出的改善预期仍需后续结果检验。

## 8. 具体实例需要核实

- 基础材料、源码版本和活动 Harness 是否一致。
- 本轮事实快照的时间与范围，以及模型实际收到哪些材料。
- 缺口是否能通过登记资料补齐；若不能，具体缺的是事实、能力还是权限。
- validator 实际检查了哪些路径，probe 是否适用于当前目标。
- 控制请求、宿主采纳与任务评价是否有彼此关联的证据。
