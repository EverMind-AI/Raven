# 装配与状态：从候选产物到可运行 Harness

本篇解释当前实验如何使用原生入口，以及生成内容的生命周期。适用范围与术语见[阅读入口](index.md)，模块分工见[设计](../../../docs/design.md#5-装配与观测)。

## 1. 原生装配与实验适配各负责什么

原生 `build_runtime` 接收 Config、RavenConfig 及显式传入的 provider、session manager、HostWiring、ContextEngine 等对象，构造插件注册表、记忆后端、工具、Hook、TokenWise 策略和 AgentLoop，返回 RavenRuntime。

实验适配层将声明接受的候选转成这些原生输入，保留构造和绑定证据，再由原生 runner 执行任务。它不建立另一个 AgentLoop，也不在已运行的 Loop 上任意替换原生四模块。公共策略如何经这些入口接入，见[四策略与信息通道](strategies-and-channels.md)及各策略的接入材料。

一组装配对象及其生命周期构成一个运行代（runtime generation），RavenRuntime 承载这组对象。原生系统还存在受控的配置应用入口；这些入口不意味着所有成员都能热替换。当前实验对实际发生改变的候选在执行边界重建进程和运行时。

## 2. 候选中有哪些不同内容

| 内容 | 责任 |
|---|---|
| Plan | 说明理解、所选改造目标、原因、预期、核验方式及所需状态 |
| Artifact.values | 按目标提供原生配置、内容资源或工厂引用等 payload |
| Artifact.files | 配套代码或其他文本文件，放入物化产物包 |
| Candidate | 将方案与产物关联到宿主附加的基线身份和契约身份 |
| Validation | 已执行检查的错误与观察；passed 仅由是否有错误决定 |

精确字段、原生类型和必填要求由 schema 提供。Plan 的状态说明只是设计交代，不会自动创建状态存储或授予资源访问能力。省略必要的状态实现，不能由填写说明补足。

## 3. 共同声明如何贯穿两个出口

1. 原生类型、配置模型、工厂贡献协议及作用说明形成宿主 Target。
2. 当前实例条件决定入口是否可达，manual 进一步收窄目标、字段和 phase。
3. 同一 Declaration 渲染模型可见信息、Plan/Artifact schema 和解析检查。
4. 宿主接受候选时附加基线与有效契约身份；验证和安装时重新核对。这些身份用于核对基线与契约，不是持久任务修订编号，也不覆盖产物的每个字节。
5. 装配根据同一 Target.binding 选择原生入口，未知绑定会被拒绝。

本组知识资源解释上述机制，但不能扩展这一范围。当前生效声明是模型输出与宿主接收的共同依据。

## 4. 配置与文件如何合成

当前 worker 保留宿主给定的初始 Baseline，并维护任务中累积的改动产物 Artifact。每次新装配从初始基线与累积产物得出有效配置，不把上一代的可变内存对象当作下一代配置来源。

合成规则需要在生成时明确：

- 字典递归合并，未指定的键保留。
- 列表和标量由新值整体替换，列表元素不会自动按名称逐项合并。
- 支持文件按相对路径覆盖；未再提交的既有文件仍保留在累积产物中。
- 当前没有通用的删除指令。None 的含义取决于具体原生字段，不能把它普遍当作“删除”。

因此，要修改贡献列表中的一个元素，应提供该目标最终需要保留的列表。要改变文件内容，应提交完整的新文本；不能把“只写一行差异”当成文件 patch，除非对应入口明确支持它。

### 4.1 代码与工厂引用

`Artifact.files` 物化为按内容标识的独立 Python 包。原生工厂引用采用 `module:callable`；如果对应模块在当前产物包内，适配层解析到该包，否则保留已有可导入模块引用。

生成包内的模块协作应使用合适的包相对导入，避免依赖进程里偶然存在的顶级模块。重新物化时，已有包内容与当前产物不符会被拒绝复用。Candidate 内嵌映射并非深度不可变，基线与契约身份也不保证 artifact 内容未变；解析合法、已通过检查的具体内容和实际加载内容之间的一致性仍需调用方维护，改变内容后应重新验证。

### 4.2 Prompt 与 Skill 资源

Bootstrap 内容和 Skill 文件分别落在 agent home 的原生位置。宿主检查相对路径和父目录范围，以原子替换写入受管理文件，并保存原内容用于失败恢复。

agent home 不是任意任务工作目录。改变 Harness 不能通过重设 home 丢失当前任务的会话和资源身份。

## 5. 各类原生入口怎样接入

| 产物形式 | 当前适配动作 | 成功需要确认什么 |
|---|---|---|
| 配置值 | 合成并通过原生配置模型恢复 | 字段合法，消费路径读取了期望的值 |
| Bootstrap / Skill | 物化到原生资源位置 | 内容可发现、可读取，实际使用情况另行验证 |
| 参与方法引用 | 导入工厂引用，按引用分组并创建受声明约束的 ParticipantHook | 工厂调用及选中方法检查发生在首次创建 turn 席位时；phase 和返回检查在调用时发生 |
| 插件贡献 | 生成原生 manifest 与薄工厂包装，调用原生插件装配 | 注册、构造和绑定到宿主的对象一致 |
| ContextEngine 工厂 | 使用宿主构造的 PluginContext 创建对象，交给原生 instance socket | 基础接口成立，并在实际上下文路径使用 |
| MCP 配置 | 交给原生连接管理；解析产物内的命令/参数路径 | 正常启动连接成功，工具发现和执行另需证据 |

Participant 工厂按原生约定无参创建 turn 实例。插件贡献工厂接收 PluginContext。ContextEngine 工厂由本适配层提供相应构造上下文。不能把不同工厂的输入形式混用。

原生构造中有些错误会被记录后降级处理；实验包装额外保留请求贡献的构造和绑定依据，避免把“Loop 仍然能启动”误认为“候选组件已接入”。

未被选中的记忆后端工厂可以只注册而不构造。服务对象构造完成后还需要启动，观察者还需要附加，MCP 还需要连接。这些生命周期阶段不能互相替代。

## 6. 进程、执行边界与换版

调用方持有 Worker 控制对象；子进程持有 RavenRuntime。子进程使用自己的配置路径和工作目录，通过固定 JSON 请求处理 inspect、run、probe 和 close。这个边界用于配置与资源归属，不等于 Python 安全沙箱。

当前 worker 对相关操作加锁，避免执行与安装交错。安装过程为：

1. 读取当前装配并核对候选的基线与契约身份。
2. 没有改动或合成产物相同时，继续使用当前运行时。
3. 快照受管理文件的旧内容及必要属性，关闭旧运行时。
4. 用新的累积产物装配并启动运行时；新内容由装配中的 install_content 写入，成功后返回新的 Inspection。
5. 激活失败时恢复内容与旧产物，并尝试重新启动旧 Harness；取消路径结束执行，不自动重启。

旧 Harness 的重新启动也可能失败，应保留并报告错误，不能把“有恢复路径”理解为恢复必然成功。文件恢复只覆盖受管理内容，不撤销工具或外部服务已经产生的副作用。

`generation.generate` 对有改动的候选调用传入的 validator；空改动方案直接返回沿用结果。`install` 自身复核声明和实际启动，不自动重跑静态检查或行为 probe，也不检查一份历史 Validation 凭证。调用方必须明确采用了哪些检查，并安装通过这些检查的同一份产物内容。

## 7. 状态的所有者和寿命

| 状态 | 通常的所有者 / 范围 | 跨越边界时的行为 |
|---|---|---|
| 某次模型响应与工具提案 | 当前 iteration | 可能因回退从消息中移除 |
| Participant 属性 | 当前 turn 的参与者实例 | turn 内可共享；不会因消息回退自动重置；下一 turn 不承诺保留 |
| Hook、工具、服务、引擎对象属性 | runtime generation | 同代多个 turn 可以共享；重建后需重新构造 |
| 会话记录 | 原生 SessionManager 和 agent home | 通过相同会话身份继续读取 |
| 任务文件与持久资源 | 明确的 workdir、home 或外部存储 | 由实际存储决定，不能由重启推断回滚 |
| 当前 Task 的反馈和版本关系 | workflow.improve 与 worker 的生成、执行记录 | 显式反馈关联任务、执行和候选；把评价归纳为行为要求由同级 Analyst 承担 |

使用共享状态前应说明资源位置、读写主体、初始化、结束及失败处理。若希望一个 review 读取工具写入的证据，要确保它们使用同一资源身份，并确认写入已经完成。

避免把任务级、会话级与 generation 级状态都放在同一个模块全局变量中。进程终止会丢失这些内存值，单独的验证进程也不会天然共享它们。

## 8. 释放与取消

正常资源释放沿原生 dispose 路径进行，包括服务/观察者、子任务、MCP、Skill watcher 和记忆后端等。顺序需要考虑仍在写入或使用其他资源的组件。

超时和取消会终止 worker 进程生命周期，尽量保留已经写出的观察记录。强制终止不保证执行完每个组件的普通停止代码，生成机制不能只依赖进程退出时的最后一次写入保存关键业务状态。

## 9. 具体实例需要核实

- 当前有效声明与基线身份，候选是否针对同一版本。
- 配置合成后的真实值、已有贡献列表和支持文件。
- 工厂调用、对象绑定、服务启动和 MCP 连接状态。
- 所需状态的实际存储与不同组件使用的身份是否一致。
- 已做检查的范围、失败恢复结果和运行时资源是否释放。
