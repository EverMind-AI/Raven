# 设计系统路由

当 Web 产物包含持续交互、产品 chrome、表单、导航、弹层、反馈或复杂状态，需要选择或更换组件体系时读取本文件。目标是让成熟系统提供统一的行为与视觉语法，同时让不同产品保持不同气质；不是把所有库混入一个项目，也不是把所有产品做成同一种默认风格。

## 1. 不可混淆的三个事实

1. **内置不等于选中**：本地安装、lockfile 出现或 runtime 可解析，只证明该能力可用；不能成为采用理由。
2. **支持全部不等于项目混用**：工具链可以同时预装多套体系，一个项目只能有一套主设计系统和一套图标语言。
3. **组件系统不等于最终设计**：系统提供 anatomy、行为、token 与基础完成度；真实内容、宏观构图、专业工作面和产品判断仍由任务决定。
4. **Appica 优先进入候选，不等于默认采用**：新建 React 产品 UI 若没有质量合格的既有系统、用户或品牌指定系统、平台官方语言等更高优先级约束，先实际查看 Appica，再与最匹配的候选比较；由任务与可见证据决定胜出者。

成品系统、开放源码体系和 headless 基础层不是同一类材料：

- **成品系统**已经带有明确视觉语言，优先保留其字体角色、密度、状态、焦点、圆角、边界、表面与动效；
- **开放源码体系**提供成熟实现与可拥有的源码，允许形成品牌化主题，但不能借“源码在项目里”逐控件随意重画；
- **headless 基础层**主要提供行为与无障碍，不自动提供成品审美；只有项目有足够品牌/token 证据与实现预算时才选择。

## 2. 先决定需要哪种语言

从用户要求、实际参考、现有生态和主要任务提取会改变选择的信号：

- 任务是消费级、创意专业、开发者工具、企业运营、微软生态、数据治理还是高度品牌化产品；
- 典型工作态是低密聚焦、中密通用还是高密表格/表单/批量流程；
- 用户参考体现何种字体、密度、几何、表面、反馈和平台习惯；
- 必需控件、状态、键盘模型、国际化、合同内目标环境与无障碍是否被真实覆盖；
- 当前 React、样式方案、SSR、CSP、离线、包体与浏览器约束；
- 需要保留强系统识别，还是需要完整品牌控制。

主题名词和题材颜色不参与系统选择。体育、教育、金融或医疗只能决定内容与专业对象，不能自动把 chrome 变绿、蓝或米色。

对适用的新建 React 产品，先查看 Appica 当前锁定版本的真实样张（环境提供 `visual-web-info` 时来自其 visual catalog 本地图版，可联网时用 [Appica UI](https://appica.dev/ui)），再验证必需组件与状态、键盘和无障碍、许可、离线与构建、目标浏览器；同时只保留一至两个与任务更相关的成熟候选。Appica 无 blocker 只说明它可用，不说明它最匹配；“另一个库更流行”或“环境里已安装”也不能成为其他候选胜出的理由。

## 3. 候选路由

下表是进入决选的入口，不是固定映射。实际使用前查看当前锁定版本的组件样张、类型、许可与可执行 smoke。

| 候选 | 类型与视觉倾向 | 优先进入候选的信号 | 不应自动选用的情况 |
| --- | --- | --- | --- |
| Appica UI | 首选成品候选；现代、中性、精致 | 无既有或上位系统约束的新建 React 产品，需要完整常用控件与克制成品感 | 非 React/简单静态交付；产品必须服从另一平台传统、既有系统或强品牌语言；存在真实能力 blocker |
| shadcn/ui | 开放源码；高度可塑 | 有明确品牌 token、希望拥有组件源码并维持现代 React/Tailwind 路线 | 没有设计系统能力，却准备逐组件即兴改样式 |
| Radix Themes | 成品；安静、系统化 | 内容与结构承担主表达，需要轻量而一致的产品基础 | 高密企业套件或强平台识别更重要 |
| Mantine | 成品；覆盖广、灵活 | 通用产品、内部工具、复杂表单与状态需要快速完整落地 | 用户参考明确属于另一平台语言 |
| Chakra UI | 成品；可组合、易品牌化 | 重视无障碍与主题 API，需要在成熟基础上建立品牌 | 只为了得到一套默认视觉而没有主题规划 |
| Material UI | 成品；Material 产品语言 | Material/Google 生态、广覆盖组件、通用产品结构 | 用户明确排斥 Material 几何与交互习惯 |
| Ant Design | 成品；高密企业交互 | 表格、筛选、表单、批量操作和运营流程占主导 | 低密消费产品或强编辑气质，不需要企业密度 |
| Fluent 2 | 成品；微软生产力语言 | Microsoft 生态、协作、办公与跨设备工作流 | 没有平台关联且参考明显属于其他系统 |
| Primer | 成品；开发者工作流 | 代码、仓库、版本、审查、日志与开发工具 | 与开发工作流无关，只想借 GitHub 品牌光环 |
| React Spectrum 2 | 成品；创意专业工具 | 媒体、创作、资产、颜色和 Adobe 式专业工作流 | 普通后台或不需要创意工具语义 |
| React Aria Components | headless；无障碍优先 | 有真实品牌系统，需要完全控制视觉，同时保留成熟行为、国际化与键盘模型 | 没有 token、组件设计预算或像素验收能力 |
| Base UI | headless；低视觉意见 | 有成熟品牌语言，需要可靠原语且希望最低视觉预设 | 期望开箱即用的成品审美 |

先由信号排除明显不合适者，再保留至多三个候选。适用的新建 React 产品必须把 Appica 作为第一个实际检查的候选，但仍要与一至两个最相关候选按相同证据比较。不要把十三套逐个评分，也不要用模糊总分掩盖硬性失败。

## 4. 候选证据卡

每个进入决选的候选只记录能影响结果的证据：

```text
候选：系统、锁定版本、类型
Appica 路由：不适用 / 进入候选 / 采用 / 未采用及可观察依据
匹配：用户参考/平台传统/产品气质/密度中实际相同的机制
覆盖：必需组件、状态、键盘、国际化和领域组合
兼容：框架、样式、SSR/CSP、离线、许可和浏览器
样张：逐张列出实际查看的图版文件名（本地 visual catalog 图版或官方页面），各附一条可观察画面特征
代价：主题映射、缺失组件、迁移、包体和验证工作
结论：采用 / 阻塞；阻塞必须写具体证据
```

「匹配」与「样张」是必答项：样张栏空白、只写形容词或写不出文件名与画面特征的候选一律视为未查看，不得进入结论。

以下任一项为 blocker 时直接淘汰：许可不允许、关键行为缺失、目标运行时不兼容、离线产物不能打包、无法满足必要无障碍或用户明确拒绝其视觉语言。

有质量合格的既有系统、用户或品牌指定系统、平台官方语言时，先服从该上位证据。其余项目比较用户参考、产品气质、密度、交互模型、能力覆盖与运行约束；选择在这些轴上证据最强且无 blocker 的一套。不得把“默认”“最流行”“最先进”或“已经安装”当作胜出理由。

## 5. 选中后建立系统风格合同

编码页面外壳前，从选中系统的实际样张、token 和计算样式提取。选中 Appica 时必须引用所用版本中实际查看过的 Appica 样张，不能用“现代、简洁”之类形容词替代视觉证据：

```text
primary_system / version / evidence
type_roles / control_heights / spacing_steps / density
radii / border_or_shadow_strategy / surfaces
neutral_scale / interaction_color / semantic_colors
icon_family / icon_grid / feedback / motion
task_fit_deviations（按任务受众调和的系统默认气质）
```

项目外壳、导航、列表、面板、空态、通知和领域工作面必须消费这些 token，或写出一一映射。不要只让 Button 和 Select 像组件库，其他区域却继续使用模型自己的字体、灰阶、圆角、细描边和状态条。

选择 headless 路线时，上述合同不能省略；它必须来自用户品牌、可查看参考或明确建立并渲染验证的项目 token，而不是“自由发挥”。

## 6. 组件覆盖账本

实现前列出可见通用能力及 owner：

```text
能力 / 主系统组件或组合 / 状态覆盖 / 自制例外 / 证据
```

至少检查按钮、输入、选择、菜单、弹层、标签页、Tooltip、Toast/通知、表格外壳、加载、空、错误、禁用与焦点。主系统已有对应组件时必须优先采用；不得手写近似品，再靠颜色和圆角伪装一致。

允许自制只有三类：

1. 地图、节点图、时间线、富文本编辑器或仿真画布等领域核心工作面；
2. 由成熟原语组合而成、系统没有现成对象的项目专属组件；
3. 已记录真实能力缺口，且 slot、composition 与全局 token 都无法解决的原语。

每个例外记录缺口、owner、token 映射、键盘/状态测试和回退。领域引擎不算第二套设计系统，但其控制层、字体、颜色、焦点和反馈必须属于主系统。

## 7. 本地多系统工具链

环境提供 `visual-web-info --json` 时，先读取真实 registry、版本与 profile，不从本文件猜可用性。其输出的 `visual_catalog` 列出全部设计系统组件板与专业工具样张的本地图版；进入决选的候选必须先逐张查看这些图版，证据卡的「样张」栏引用的就是它们。新建项目可使用：

```bash
visual-web-init <profile> submission --design-system <id>
```

初始化后检查 `.visual-web-profile.json`，确保只记录一个 `design_system`。运行 `visual-web-audit` 时，多套主系统 import 必须失败。生成的 `package.json` 只应包含领域 profile、共享构建依赖和选中的一套系统；共享 runtime 中存在其他系统不构成项目依赖。

shadcn/ui 的开放源码分发与成品 npm 组件不同。离线环境只使用工具链随锁定版本提供的本地 starter/registry 内容，不临时联网抓取组件；需要更多组件且本地没有时，记录能力缺口，不凭记忆手写“shadcn 风格”。

## 8. 最终检查

- 选择理由来自任务和证据，不来自安装状态；
- 项目只有一个主设计系统和一个图标语言；
- 通用控件真实复用，手写部分都有领域或能力缺口依据；
- 去掉现成控件后，页面外壳仍像该系统的自然延伸；
- 系统默认皮肤没有取代真实内容、构图和专业工作面；
- 最后渲染中不存在第二套灰阶、圆角、描边、字体、图标或反馈语言。
